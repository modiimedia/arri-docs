title: Bring Your Own Server Language
description: A comprehensive guide to building a custom server implementation for Arri RPC in any language.

Because Arri is completely language-agnostic, you can implement a server adapter in any programming language you choose. This guide explains how to generate a compatible **Arri App Definition (AAD)** and hook into the CLI workflow.

---

## What a Server Implementation Needs to Do

Every Arri RPC server implementation must perform three main tasks:

1.  **Expose the App Definition**: Provide a mechanism (typically an HTTP endpoint or a generated static file) that returns the standardized Arri App Definition (AAD) JSON structure representing your server's endpoints and parameter/response structures.
2.  **Expose RPC Handlers**: Route requests matching the patterns registered in the definition, validating incoming parameters at the runtime boundary.
3.  **Integrate with the CLI**: Expose a plugin or configuration interface so `arri dev` knows how to hot-reload your server and request the latest schema metadata.

---

## Exposing the Schema Definition

The simplest way to integrate a custom server is to output a static `AppDefinition.json` file during your local build or compilation step.

For example, if you are implementing a server in Python or Rust, you would write a compiler utility or startup hook that serializes your server-side classes/structs into standard JTD schemas, outputting:

```json
{
  "schemaVersion": "0.0.1",
  "procedures": {
    "sayHello": {
      "transport": "http",
      "method": "post",
      "path": "/say-hello",
      "params": "SayHelloInput",
      "response": "SayHelloOutput"
    }
  },
  "definitions": {
    "SayHelloInput": {
      "properties": {
        "name": { "type": "string" }
      }
    },
    "SayHelloOutput": {
      "properties": {
        "message": { "type": "string" }
      }
    }
  }
}
```

Then, developers simply run:

```bash
arri codegen ./AppDefinition.json
```

---

## Standardizing Runtime Validation

When handling requests, your server must ensure:
-   HTTP requests use the proper methods and paths defined in the schema.
-   Payloads are parsed and strictly match the JSON Type Definition models. If parsing fails, return a standard `400 Bad Request` or an `ArriError` payload:

```json
{
  "statusCode": 400,
  "statusMessage": "Bad Request",
  "data": "Missing required field 'name' on model SayHelloInput"
}
```
